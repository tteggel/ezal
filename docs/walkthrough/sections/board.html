1. A board wakes up

What happens between power reaching the Pico and the dashboard appearing in your browser, and why does a perfect start leave the motors still?

Picture the dish parked wherever it was last left. You plug in the board. Shortly afterwards it has joined your Wi-Fi, it knows which way the dish is pointing, and a dashboard is waiting in your browser. Nothing has moved. That stillness is the first thing the program arranges, and to see how, we start with the only parts of the board that can move anything.

Four pins that can move a dish

The Pico is a small circuit board with a row of metal pins along each edge. A program running on it can put one of two voltages on a pin: 0 volts, called low, or 3.3 volts, called high. ezal uses four pins this way. Try them.

Each pin runs to an electronic switch on a second board, the interface board. A high pin closes its switch, and the closed switch connects one input of the control box to ground, the wire that carries the box’s 0 V. That connection is exactly what a button on the box’s front panel makes when you press it. The control box cannot tell the difference: it runs the motor for as long as the connection lasts. A small light on each wire shows which pins are high. Chapter 4 opens one of these switches up.

So the firmware, the program on the Pico, has a narrow job. Many times a second it decides whether each of GP10, GP11, GP20 and GP21 should be high or low. You just made that decision with a click. The firmware makes it only after a long list of things has been checked, and the rest of this walkthrough is that list.

Startup, one part at a time

When power arrives, nothing is in charge of those four pins. Startup is the business of taking charge: of the pins first, then of everything else the program needs, in an order chosen so that the pins are never left unattended. Drag the slider through a normal start. The dark name tags show which piece of the program holds each part of the board.

Then choose one of the three faults and drag again. Watch where startup stops, and look at the four pins. The rest of this chapter takes the steps one at a time.

First, the pins

For the first few milliseconds ezal is not running at all. A small loader built into the chip finds the program stored on the board and starts it. Until then nobody drives the four pins, and a resistor beside each switch holds it open.

How the program got onto the board

You build ezal on your own computer with Cargo, Rust’s build tool, which turns the source code into instructions for the Pico’s chip. Running cargo run -p ezal-firmware --release builds the program, writes it to the board through a debug probe (a small adapter wired to three of the board’s pins) and then shows the messages the running program logs. Without a probe, ./scripts/build-uf2.sh produces a file that you copy to the Pico over USB while holding its BOOTSEL button; you get no log that way. Your Wi-Fi name and password are built into the program, so changing them means building it again. The development guide has the whole procedure.

Then, a question about the last run

The second thing main does is ask the chip why it restarted. The answer matters because of a safety device called a watchdog: a countdown inside the chip that restarts the whole board if it ever reaches zero. ezal sets it to 500 ms, half a second, and the code that controls the pins puts it back to the top each time it finishes a round of work. If the program freezes, nothing resets the countdown, and half a second later the chip restarts.

A restart is the right answer to a freeze, but a poor moment to carry on as if nothing had happened: a motor may have been running when the program stopped. So if the chip reports that the watchdog caused this restart, main keeps the pins low and goes no further until a person resets the board.

One thing the watchdog does not promise is how quickly a switch opens after a freeze. This chip can hold a pin at its last level through a restart, until the new start reaches the line marked 2 above. How long that takes has to be measured on the real board, and it has not been yet. Chapter 7 collects everything that is still unproven.

One task keeps the pins

ezal is built from a handful of tasks: independent loops that take turns, each running until it has to wait for something. The direction task is the one that matters most. Its loop is short. It looks at the latest request and the latest position, decides what each pin should be, sets the pins, resets the watchdog, and waits, never for longer than a tenth of a second. Then it goes round again.

Because this task alone owns the pins, there is exactly one place in the whole program where a pin can go high. And because the watchdog is reset only at the end of each round, a watchdog that stays quiet means that place is still doing its work.

Next, the sensor

The dish’s position arrives as two voltages, and a separate chip on the interface board measures them. The code calls it adc, for analog-to-digital converter, and chapter 2 is about what it measures. Before trusting it, main tests it. Does a chip answer at all? Does it remember settings written to it? Do two opposite test patterns survive being written and read back? Then it takes one reading from each input for the log. The whole test, which the code calls a POST (power-on self-test), must finish within 500 ms.

If the test fails, main stops for good. Notice what never happens: the radio is not switched on, so no dashboard appears, and the only record of the failure is a log message that takes a debug probe to read. Notice also what keeps happening. The direction task was started earlier, so the pins are still held low and the watchdog is still being reset. The board is running, unreachable, and still.

Last, the radio

Only now does main switch on the Pico’s radio and start the dashboard’s web server and the remaining tasks. Its work done, main ends, and the tasks run on. One of them joins your Wi-Fi network and asks it for an address. When it has both, it flashes the light on the Pico three times. That light is wired to the radio chip and has nothing to do with the four direction pins; three flashes mean only that startup is complete.

If there is no network to join, that task tries again, and goes on trying. Meanwhile the sensor is being read and the direction task is running, but it will not raise a pin while the network is down. A controller that nobody can reach has no business moving a dish, and chapter 3 returns to that.

Why nothing moved

Go back to the last step of a normal start. Everything is running, and all four pins are at 0 V. The direction task is holding them there because two things are missing. Nobody has asked for movement, and chapter 3 is about who may. And the firmware cannot know how recently the motors last ran, so it makes them rest for 15 minutes unless you tell it they already have; chapter 4 covers that.

A third thing is already arriving, about ten times a second: the dish’s position. The direction task will not raise a pin without a position that is both recent and believable. What makes a position believable is next.

2. Turn voltage into trustworthy position

Before the firmware moves the dish it must know where the dish is. All it has to go on is two voltages. What turns a voltage into a position worth trusting?

The firmware never assumes that running a motor for one second turns the dish by a known amount. Motors slow under load, and a dish keeps moving after its power is cut. Instead, the firmware measures. Inside the rotator, each axis turns a variable resistor along with the dish, and the control box turns that into a voltage on a wire: one wire for azimuth, the direction the dish faces around the horizon, and one for elevation, its tilt above the horizon. As the dish moves, the voltages change.

A voltage too big to measure

The control box’s manual says each of those wires can carry up to 4.5 V. The sensor chip that has to measure them runs on 3.3 V and must not be shown more than that. So on its way to the sensor, each wire passes through a chain of resistors. A resistor resists the flow of electricity, and along a chain of them the voltage falls steadily, from whatever the control box supplies at one end to zero at the other. Measure part-way down the chain and you get a fixed fraction of the voltage. Drag the left end.

The chain has three resistors: 33 kΩ inside the control box, then 68 kΩ and 82 kΩ on the interface board. (kΩ means thousands of ohms, the unit of resistance; only the proportions matter here.) The sensor measures above the last one, so it sees 82 parts out of 33 + 68 + 82 = 183, about 45 %. The manual’s 4.5 V arrives as 2.02 V.

From voltage to number to angle

The sensor measures a voltage and hands the Pico a whole number. ezal sets it up so that each count is worth 2 millivolts (thousandths of a volt, written mV). The sensor can say 772 mV or 774 mV and nothing in between.

A number of millivolts is not yet a position. The link between the two is made by measurement: drive the dish to each end of the travel you intend to use, and write down what the sensor reports there. The numbers checked into the code say that azimuth reads 114 mV at 0° and 2033 mV at 360°, and that elevation reads 1281 mV at 0° and 58 mV at 90°. Everything in between is taken to lie on a straight line. Drag the dish.

Three things are worth noticing. Azimuth’s voltage rises as the dish turns clockwise, but elevation’s falls as the dish tilts up: its line slopes the other way. The firmware does not mind, because it only ever uses the two measured ends.

In the close-up, the sensor’s answer moves in steps. The dish has to turn about 0.375° in azimuth, or 0.147° in elevation, before the number changes at all, and the angle the firmware computes is always the middle of a step.

And the lines end at 360° and 90° because those are the ends that were measured for this installation. The rotator itself can turn further, 450° around and 180° over the top, but using that travel means measuring new ends first.

These numbers are not stored anywhere else. To recalibrate, you measure again, edit them, and rebuild the firmware.

Readings that cannot be believed

Not every number is a position. A wire can work loose, short to ground, or touch the 3.3 V supply, and the sensor will faithfully report whatever voltage results. So before converting a reading, the firmware asks whether a working rotator could have produced it. Drag the reading along the sensor’s whole range.

A reading of 0 mV, or of 3200 mV and above, sits at an edge of what a sensor powered from 3.3 V can measure. It might be a real voltage or a broken wire, and there is no telling which, so it is refused. A reading between the measured ends is fine. Just outside them there is a judgement to make. Real signals wobble by a few millivolts, so a reading up to 25 mV past a measured end is accepted and counted as exactly that end. Anything further out is refused.

Refusal is not a small thing. If either voltage is refused there is no position, and with no position no pin may go high.

A reading is a statement about the past

A believable reading still has a flaw: by the time anyone uses it, it is old. Measuring two voltages takes time, and then the result waits until the direction task next looks at it. The dish may have been moving all the while.

So every reading carries a time, and the firmware is careful about which time. The feedback task notes the clock before it starts measuring the first voltage, not after it finishes the second, and a reading’s age is counted from that earlier moment. Drag “now”.

Two rules use these times. A read that takes more than 150 ms is thrown away the moment it arrives; try 151. And any reading stops counting once it is more than 500 ms old; try 501.

A read can also hang, if a wire to the sensor breaks in the middle of one, for instance. After 500 ms the feedback task gives up on it and does not talk to the sensor again until the board is reset, for the same reason as at startup: a conversation cut off halfway can leave the wires in an unknown state. With no new readings, nothing moves.

Why 150 ms?

The two limits are related. A reading has to last until its replacement arrives, and in the worst case the replacement is slow as well. Drag the read time.

Room to stop

One more thing can go wrong with a perfectly good reading: the dish can be near one end of the travel that the calibration covers. Past that end the firmware would no longer know where the dish is, and its cables may not reach. A reading says where the dish was. Before driving it further towards an end, the firmware works out where it could be by now, and where it would end up if the power were cut this instant.

The reasoning is pessimistic at every step. Since the reading began, assume the motor has been running flat out towards the end: 7° a second in azimuth, 3° in elevation. When the switch opens, assume the dish coasts on at that speed for another 500 ms. And allow for the reading being off by one sensor step. If all of that added together could reach the end, the direction is refused. Drag the reading’s age.

With the dish measured at 354.93°, the reading allows clockwise travel at 155 ms old and refuses it at 156 ms. Nothing about the dish changed in that millisecond, only how long ago we looked. The other direction, away from the end, stays allowed throughout. The direction task does not wait for a new reading to find this out: it works out the moment at which the reading in hand will stop allowing a direction that is running, and wakes at that moment to cut it.

The two speeds and the coast are estimates: the fastest figures in the rotator’s manual with a margin added, and a guess at how long the dish coasts. None of them has been measured on this dish yet.

The firmware now has a position that knows how old it is and how far it can be trusted. That is half of what the direction task needs. The other half is a request, and the question of who is allowed to make one.
